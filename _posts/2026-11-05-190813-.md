## 一、让模型参考上一轮：历史消息由程序维护

最初的聊天 Demo 虽然有 `while True`，可以不断输入，但每次请求只发送当前问题。这只说明终端可以连续交互，不代表下一次请求包含之前的内容。

后来我做了三个修改。

首先，把消息列表放在输入循环外面，启动时只创建一次：

```python
messages = [
    {"role": "system", "content": "你是 Python 助教，用简短中文回答。"}
]

```

其次，让函数接收完整列表：

```python
def chat(messages: list[dict]) -> str:
    stream = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        temperature=0.9,
        stream=True,
    )
    # 后面继续收集片段，拼接并返回完整回复

```

最后，在主循环中保存本轮双方的消息：

```python
messages.append({"role": "user", "content": user_input})

answer = chat(messages)

messages.append({"role": "assistant", "content": answer})

```

消息列表因此逐轮增长：

```text
第一轮请求：[system, user₁]
第一轮结束：[system, user₁, assistant₁]

第二轮请求：[system, user₁, assistant₁, user₂]
第二轮结束：[system, user₁, assistant₁, user₂, assistant₂]

```

我实际先输入了“你好，我是小林”，下一轮问“我是谁”，模型回答了“小林”，并提到这是刚才告诉它的信息。这次结果符合历史消息改造的目标。

我需要记住的是：模型能参考前面的问答，是程序把历史重新发送给了它。当前实现的历史仍在程序内存中；我之前写过的 JSON 保存读取小练习，还没有接入这个模型聊天程序。

### `list[dict]` 不是列表的来源

我曾疑惑：

```python
def chat(messages: list[dict]) -> str:

```

这里的列表是哪里来的？后来分清了：

- `messages` 是函数参数。
- `list[dict]` 是类型注解，表示预期接收“由字典组成的列表”。
- 真正的列表在主程序中通过 `messages = [...]` 创建。
- 调用 `chat(messages)` 时，把这个列表交给函数。

`list` 和 `dict` 是 Python 自带类型，不需要导入；注解本身不会创建数据，也不会自动完成所有运行时类型检查。

如果函数参数改叫 `history`：

```python
def chat(history: list[dict]) -> str:
    # 后续请求使用 messages=history
    ...

```

主程序仍然可以调用 `chat(messages)`。调用处和函数参数处的变量名不必相同，重要的是传递了什么对象。

## 二、流式输出中的显示与返回

我继续拆解了：

```python
print(text, end="", flush=True)

```

- `end=""`：打印后不自动换行，让下一个文字片段接着显示。
- `flush=True`：立即刷新输出，让接收到的片段尽快出现在终端。

所有片段收完后，用空的 `print()` 换行，再返回拼接后的文字：

```python
print()
return "".join(parts)

```

这让我区分了两件事：函数可以在运行过程中逐段打印，同时在结束时返回一份完整字符串。

课程网页中还出现过类似 `[K` 的显示残留。对应 Demo 使用了终端控制序列来清理 `thinking...` 提示，而网页终端没有正确处理这些字符。它属于显示问题，不能仅凭这段字符就认为模型请求失败。

另一次，网页只显示“连接已断开”。课程前端在日志连接出错时会显示这个统一提示，它本身并没有告诉我 Python 的具体错误。排查时可以进入云端 IDE，直接运行脚本，区分网页运行通道问题与程序错误。

## 三、Demo 01：同一段输入，聊天与续写有什么不同

`demo_01_next_token.py` 使用同一个模型接口，提供两种 system 提示：

- `chat`：作为聊天助手回应用户。
- `complete`：作为续写引擎，把给定文字接着写下去。

这里的 `complete` 是课程自己定义的模式名称，两种模式都调用 `chat.completions.create()`，没有切换成另一个 API。

核心函数是：

```python
def _build_messages(prefix: str, mode: Literal["chat", "complete"]) -> list:
    if mode == "complete":
        return [
            {"role": "system", "content": COMPLETE_SYSTEM_PROMPT},
            {"role": "user", "content": prefix},
        ]

    return [
        {"role": "system", "content": CHAT_SYSTEM_PROMPT},
        {"role": "user", "content": prefix},
    ]

```

我对这段代码的理解：

1. `prefix` 是输入文字。
2. `mode` 决定选哪份 system 提示。
3. `return [...]` 真正创建并返回消息列表。
4. `complete` 分支执行 `return` 后，函数立即结束，所以后面不一定要写 `else`。

`Literal["chat", "complete"]` 是类型注解，表达允许的预期选项；这段代码没有自动拒绝其他字符串，其他值也会走下面的聊天分支。

### 这份 Demo 实际展示了什么

代码中的函数叫 `show_top_candidates()`，注释也提到了概率分布，但当前实现只收集并显示完整生成结果，没有读取候选 Token 的概率。

因此，这份代码直接支持的观察是“同一段文字在不同上下文要求下如何得到不同回应”，不能仅凭它就说自己看到了模型内部的概率表。

这部分我主要完成了代码阅读与逐段理解，没有在本次记录中保留两种模式的完整对比输出，所以不把某个示意回答写成自己的实测结果。

### 几个新增语法

条件表达式：

```python
mode_label = "续写模式" if mode == "complete" else "对话模式"

```

等价于：

```python
if mode == "complete":
    mode_label = "续写模式"
else:
    mode_label = "对话模式"

```

`!r` 用于显示变量的表示形式：

```python
result = "你好\n小林"
print(f"模型输出：{result!r}")

```

会把换行显示为 `\n`，并让引号等细节可见，适合检查模型实际返回的字符串。它不会修改 `result`。

元组解包：

```python
for title, prefix in PREFIXES:
    ...

```

`PREFIXES` 的每一项包含标题和输入文字，循环时分别交给两个变量。四组输入各运行两种模式，完整执行通常会产生八次请求。

## 四、Demo 02：system、user、assistant 如何配合

第二节固定问题，分别用“严谨学者”“5 岁小朋友的语言”“只能用 emoji”三份 system 提示。

三种角色的分工是：


| 角色 | 用途 |
| ----------- | ------------ |
| `system` | 提供角色、回答方式和约束 |
| `user` | 提供当前问题或补充要求 |
| `assistant` | 保存模型的历史回复 |


这个 Demo 的两个新理解是“课程辅助函数”和“遍历字典”。

### 辅助函数把重复代码封装起来

```python
from _env import chat_stream

```

和我之前从 `helpers.py` 导入检查函数一样，这里从课程的 `_env.py` 导入功能。配置、请求和流式收集已经封装在里面。

```python
def ask(system: str, user: str) -> str:
    msg = chat_stream(
        [
            {"role": "system", "content": system},
            {"role": "user", "content": user},
        ],
        temperature=0.3,
    )
    return msg.content or ""

```

这里的辅助函数返回消息对象，所以要读取 `msg.content`。这和我之前自己写的、直接返回字符串的 `chat()` 不完全一样。

`msg.content or ""` 表示有正文就返回正文，否则返回空字符串。判断返回值结构时，要看具体函数定义，不能只看名字。

### `.items()` 同时取得键和值

```python
for name, sys_prompt in SYSTEM_PROMPTS.items():
    answer = ask(sys_prompt, QUESTION)

```

`name` 接收字典的键，用来显示实验名称；`sys_prompt` 接收字典的值，才是实际发给模型的要求。

三次调用各自构造新消息，不继承彼此的问答。这部分代码我已经阅读和理解；提示效果仍然需要通过实际输出核对，不能把“写了要求”直接当作“模型必然遵守”。

```python
def chat_with_system(system_prompt: str, user_message: str) -> str:
```

```python
from _env import chat, get_model_id, make_client
```

第一处是参数名：


应该写成：

```python
messages=messages
```

## 六、Token、上下文窗口和成本

第三节把几个经常混用的概念分开了。

### 字符数和 Token 数

```python
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
text = "Hello, world!"
ids = enc.encode(text)

print(len(text))
print(ids)
print(len(ids))

```

- `len(text)` 是 Python 字符串长度。
- `ids` 是 Token ID 列表。
- `len(ids)` 是当前编码器下的 Token 数。

Token 不等于一个字、一个字母或一个单词。课程选择 `cl100k_base` 做练习，但不能把它对任意文本的统计直接认定为当前 CNB 模型的精确用量。

### 上下文窗口是一次请求的容量预算

可以先按下面的关系理解：

```text
输入 Token + 本次生成的 Token ≤ 上下文窗口

```

例如，假设窗口为 5,000 Token，输入占 4,200 Token，就还剩 800 Token 的生成空间，具体还要考虑模型单独的输出限制。

历史问答也是下一轮输入的一部分。因此，保留消息越多、消息内容越长，后面的输入通常也越大。只看消息条数，无法判断占用了多少 Token。

### 成本需要按输入与输出分别计算

```text
输入成本 = 输入 Token 数 ÷ 1,000,000 × 每百万输入 Token 单价
输出成本 = 输出 Token 数 ÷ 1,000,000 × 每百万输出 Token 单价

```

课堂里用过一个假设例子：输入 1,000 Token、单价 ¥5/百万，输出 200 Token、单价 ¥15/百万，总计是 ¥0.008。这只是算术练习，不是当前服务报价。

实际计费还要看服务价格、缓存等规则。这次没有为了演示容量限制而专门向服务提交超长输入。

## 八、Demo 04：资料注入与真实工具调用

第四节讨论模型如何获得外部信息。对我来说，最直观的例子是：项目内部公告、当前时钟、实际程序运行结果，都需要有合适的信息来源。

### 实验 1：把资料放进本次输入

Demo 用 `SECRET_FILE` 模拟内部公告，`read_internal_doc()` 返回这个字符串。它并没有真正打开文件。

程序先直接提问，再把文档和问题一起放进消息：

```python
enriched = f"""请基于下面提供的内部文档回答用户问题。

【内部文档】
{read_internal_doc()}

【用户问题】
{question}
"""

```

这个实验帮助理解“先取得资料，再把资料加入上下文，最后生成回答”的思路。当前实现没有自动检索，也不会因为把资料放进请求就修改模型参数。

### 实验 2：模型提出请求，Python 执行工具

工具的实际实现是一个普通函数：

```python
def get_current_time() -> str:
    return datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S")

```

它读取运行环境本地时间并格式化。工具说明写“北京时间”不等于自动设置了时区，仍然要看运行环境。

程序通过 `tools` 提供名称、描述和参数说明。模型收到说明后，可以返回 `tool_calls`。

```text
用户问时间
    ↓
模型返回调用请求
    ↓
Python 执行 get_current_time()
    ↓
把 assistant 调用请求和 tool 结果加入 messages
    ↓
再次请求模型，生成最终回答

```

我运行后看到的关键输出是：

```text
模型决定调用工具：get_current_time()
工具返回：2026-11-05 16:06:41
最终回答：使用了同一时间值

```

这次实际输出说明，工具调用分支被执行了，工具结果也进入了最终回答。

### `tool_call_id` 把请求和结果关联起来

消息里需要保存两部分：

```python
{
    "role": "assistant",
    "tool_calls": [
        # 模型刚才提出的工具调用请求
    ],
}

```

以及：

```python
{
    "role": "tool",
    "tool_call_id": tool_call.id,
    "content": result,
}

```

调用请求的 `id` 和工具结果的 `tool_call_id` 对应，让模型知道结果属于哪次调用。

这只是下一章的预告示例：当前代码取第一个调用，固定执行时间函数，尚未实现通用工具注册、分发和反复运行的 Agent 循环。

## 九、流式输出收集器：正文与 usage 分开处理

对应文件：`exercises/01-meet-your-ai/ex_1_3.py`。文件注释里有“练习 1.4”的旧编号，实际按文件路径定位。

这道题要求一次返回两项：

```python
(完整回复文本, 本次请求总 Token 数)

```

整理后的函数是：

```python
def stream_collect(user_message: str) -> tuple[str, int]:
    stream = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "user", "content": user_message}
        ],
        stream=True,
        stream_options={"include_usage": True},
    )

    pieces = []
    total_tokens = 0

    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            pieces.append(chunk.choices[0].delta.content)

        if chunk.usage:
            total_tokens = chunk.usage.total_tokens

    return "".join(pieces), total_tokens

```

### `usage` 是服务返回的用量统计


| 属性 | 含义 |
| ------------------- | ------- |
| `prompt_tokens` | 输入用量 |
| `completion_tokens` | 生成用量 |
| `total_tokens` | 本次请求总用量 |


开启 `include_usage` 后，服务正常支持时会返回用量信息。普通正文片段的 `usage` 通常为 `None`，包含用量的片段可能没有正文候选项。

因此，两个 `if` 必须同级：

```text
for 每个响应片段
    if 有正文
        收集正文
    if 有用量
        保存总用量

```

我曾把 `if chunk.usage` 放在正文判断里面，导致没有读到最终用量，`total_tokens` 保持为 0，测试因此失败。

### 为什么这里不使用 tiktoken 累加片段

初稿曾用编码器统计每个回复片段，再累加长度。但题目要求的是服务报告的整次请求总量；仅编码输出片段不包含全部输入，并且分段编码的结果也未必等于整段编码。

这里应该直接赋值：

```python
total_tokens = chunk.usage.total_tokens

```

因为得到的是总量，不是当前片段的增量。

另外，请求的 `messages` 必须是消息列表，我曾误传了字符串 `user_message`，后来改成了 `[{'role': 'user', 'content': user_message}]`。

修改后练习测试通过，其中一次终端显示总 Token 数为 `37`。这是那次请求的用量，不代表每次运行都会得到同一个数。

## 十、第一章核心产出：LLMClient

最后把模型访问与计数封装进 `my-agent/llm.py`，形成四个方法：


| 方法 | 对外提供什么 |
| ---------------- | ------------------- |
| `__init__()` | 创建客户端、读取模型配置、准备编码器 |
| `chat()` | 返回完整字符串 |
| `chat_stream()` | 逐段提供回复文字 |
| `count_tokens()` | 返回指定编码器下的文本 Token 数 |


下面是按照本次最终实现思路整理的复习版本：

```python
import os
from typing import Generator

import tiktoken
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()


class LLMClient:
    def __init__(self):
        base_url = os.getenv("BASE_URL")

        if not base_url:
            endpoint = os.getenv("CNB_API_ENDPOINT", "")
            slug = os.getenv("CNB_REPO_SLUG", "")

            if endpoint and slug:
                base_url = f"{endpoint}/{slug}/-/ai-ide/v2"

        api_key = os.getenv("API_KEY") or os.getenv("CNB_TOKEN")

        if not base_url or not api_key:
            raise ValueError("缺少 API 地址或密钥，请检查运行环境配置")

        self.client = OpenAI(base_url=base_url, api_key=api_key)
        self.model = os.getenv("MODEL_ID") or "deepseek-v4.1-flash"
        self.enc = tiktoken.get_encoding("cl100k_base")

    def chat(self, messages: list[dict], **kwargs) -> str:
        return "".join(self.chat_stream(messages, **kwargs))

    def chat_stream(
        self, messages: list[dict], **kwargs
    ) -> Generator[str, None, None]:
        stream = self.client.chat.completions.create(
            model=self.model,
            messages=messages,
            stream=True,
            **kwargs,
        )

        for chunk in stream:
            if chunk.choices and chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content

    def count_tokens(self, text: str) -> int:
        return len(self.enc.encode(text))

```

这里的模型默认名称沿用本次课程代码；实际优先使用环境里的 `MODEL_ID`，可用性取决于所使用的服务。

### `self` 保存对象后续需要的东西

`self.client`、`self.model`、`self.enc` 都保存在当前实例上。后面的三个方法可以直接使用，而不用每次重新写一遍初始化逻辑。

### `**kwargs` 转交额外关键字参数

例如调用：

```python
llm.chat(messages, temperature=0.3)

```

方法里的 `kwargs` 会收到类似：

```python
{"temperature": 0.3}

```

再用 `**kwargs` 把它展开，转交给下一个函数。当前实现中，`chat()` 把它转给 `chat_stream()`，后者再转给接口方法。

### `yield` 逐段提供值

`chat_stream()` 中使用 `yield`，所以调用后得到可以迭代的生成器。遍历时，函数运行到 `yield` 就提供一个片段，下一次取值时再继续运行。

```python
for piece in llm.chat_stream(messages):
    print(piece, end="", flush=True)

```

`Generator[str, None, None]` 是相应类型注解，这里主要表示会逐段产出字符串。

`chat()` 则把同一套流式输出收齐：

```python
return "".join(self.chat_stream(messages, **kwargs))

```

因此，底层请求同样是流式，对调用者却可以提供两种使用方式。

## 十一、LLMClient 的三次具体排错

### 1. 编码器名称区分大小写

我曾写成：

```python
tiktoken.get_encoding("Cl100k_base")
```

正确名称是：

```python
tiktoken.get_encoding("cl100k_base")

```

开头的 `c` 要小写。

### 2. Missing credentials：没有读到当前环境的凭据

最初初始化只读取：

```python
api_key=os.getenv("API_KEY")

```

运行测试时出现 `Missing credentials`。课程练习能运行，是因为辅助模块会尝试读取 `CNB_TOKEN`；我自己的类没有复制这部分配置回退逻辑。

修正后优先使用手动配置，否则读取平台变量：

```python
api_key = os.getenv("API_KEY") or os.getenv("CNB_TOKEN")

```

地址也做对应回退。`load_dotenv()` 的作用是加载 `.env`，它不会自动把 `CNB_TOKEN` 改名成 `API_KEY`。

### 3. 当前接口不支持非流式请求

配置问题解决后，`test_chat()` 又返回：

这是我本次使用的接口明确拒绝了非流式请求，不是 `messages` 或函数缩进错误。

解决方式是复用已经写好的 `chat_stream()`，内部流式接收，对外返回拼接后的完整字符串。这样仍然满足作业中 `chat()` 返回 `str` 的约定。

## 十二、代码通过测试后，如何真正交作业

这次我实际走了一遍 Git 与 PR 流程，也解决了一个重要疑问：云开发环境不是已经属于我的仓库了吗，为什么还要 push？

### 云开发副本与远程仓库是两个位置

CNB 云开发环境相当于一台远程电脑，`/workspace` 中是供我编辑、运行、提交的工作副本。CNB 仓库网页展示的远程 Git 仓库，需要通过 push 同步。

这里 Git 所说的“本地”，是指当前这台云开发机，相对于远程代码仓库而言；不一定是我的 Windows 电脑。

```text
编辑文件
    ↓ git add
选择改动进入暂存区
    ↓ git commit
记录到开发机上的 Git 历史
    ↓ git push
同步到自己的远程仓库
    ↓ 创建 PR
向官方仓库提交作业，请求检查
    ↓
平台运行自动测评

```

### 本次实际提交了四个文件

```bash
git add exercises/01-meet-your-ai/ex_1_1.py exercises/01-meet-your-ai/ex_1_2.py exercises/01-meet-your-ai/ex_1_3.py my-agent/llm.py
git diff --staged --stat
git commit -m "feat: complete chapter 1 LLM client and exercises"

```

提交编号是 `9ad4bc3`，统计为四个文件、增加 60 行、删除 8 行。

`git diff` 打开分页界面时，底部出现 `(END)`，只是表示显示到结尾；按英文 `q` 可以退出，回到命令提示符。

### 退出环境后，提交仍然保留

重新进入云开发环境后，我检查了：

```bash
git status
git log -3 --oneline
git remote -v

```

状态显示：

```text
Your branch is ahead of 'origin/main' by 1 commit.
nothing to commit, working tree clean

```

这表示本地有一个未推送提交，文件改动已经进入提交，工作区干净。无需再次 add 和 commit，接着 push 即可。

CNB 文档说明备份范围包含未 push 的 commit，重建环境会尝试恢复；但实际是否恢复，仍应通过状态、历史和文件检查确认。

### origin 与 upstream

之后远程 `main` 更新到了 `9ad4bc3`。这才完成“代码同步到自己仓库”的步骤。
